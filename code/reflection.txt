This assignment made the case for building a package instead of a script. I liked how sales_pipeline split responsibilities across modules using an ETL-style separation: extract.py hands back raw, unprocessed rows and does nothing else; transform.py owns all cleaning and computation; display.py is the only module allowed to format or print output. That's a form of separation of concerns — each module has a single responsibility, so a bug in formatting can't hide in the same function as a bug in math. Once I understood that split, writing main_daily_report.py from scratch was fast: I wasn't writing new logic, I was composing functions that already existed. Next time I start a project, I want to sketch this kind of module boundary before writing code, instead of discovering it after the fact.

The coercion functions (clean_currency, clean_quantity) taught me "coerce and carry on": catching a ValueError in a try/except block and returning a safe default (0.0/0) instead of letting one malformed row ("N/A", "one") crash the whole report. I'd only ever used try/except defensively, to stop my own test code from crashing — not as a designed strategy for handling untrusted, messy real-world input at a function boundary. I want more practice deciding when coerce-and-carry-on is the right call versus when a bad row should actually raise and halt the pipeline, since silently defaulting to zero can hide data-quality problems instead of surfacing them.

summarize_by_item was where I actually struggled, not just where I "learned something." I understood the group-by concept conceptually, but writing the accumulator pattern by hand — a dictionary keyed by item name, guarded with if item not in totals before I could += into it — took multiple tries. My specific bug: I nested the += inside that same if block, so only the first row for each item ever got added; every subsequent row for that item was skipped and it stayed at its initial value. I only found this by stepping through with the debugger and watching totals update in the VARIABLES panel row by row — reading the code silently hadn't been enough. My actionable next step is exactly what's assigned: write an accumulator function from a blank file, with no docstring scaffolding, and specifically check that my update step is outside the initialization guard, not inside it.

The relative imports in __init__.py (from .transform import ...) were new syntax. I now know the leading dot means "resolve relative to this package," not a top-level/absolute import. Where I still need practice is diagnosing import failures versus logic failures: a missing export from __init__.py made all 24 tests disappear at once instead of failing individually, and it took me a minute to recognize that as one ImportError rather than 24 separate bugs. Next time a whole test suite goes red simultaneously, my first move should be to check the import chain before assuming the logic is broken everywhere at once.

Finally, I can now distinguish unit tests from integration tests by what each one localizes: unit tests pointed at the exact function that was wrong, while integration tests confirmed the pipeline was wired together correctly but didn't catch that summarize_by_day was sorting in the wrong direction until I actually read the failure output instead of just checking pass/fail. That's a concrete habit to fix: read the assertion message, not just the red/green status.
